## Decision-relevant confirmations

- **Provisional default: `autogluon/chronos-2-small`.** The public card declares Apache-2.0 and 28M parameters; the exact config is `Chronos2Model` / `Chronos2Pipeline`, not original Chronos-T5. Its 8,192 context maximum, 64 output patches × 16 = 1,024 native forecast steps and 13 native quantiles include every decile 0.1–0.9. Daily 30/60/90 or weekly 13 fit natively. This supports contract suitability, not a demonstrated winner. [Small card](https://huggingface.co/autogluon/chronos-2-small), [config at `ddec01313e50b6bc58ebaa92ede81bc24a3d9f9a`](https://huggingface.co/autogluon/chronos-2-small/raw/ddec01313e50b6bc58ebaa92ede81bc24a3d9f9a/config.json).
- **TTM-r3 has short-context branches, but daily 90 needs 512 daily observations.** “12+ months” is a coarse screening rule, not sufficient native eligibility. Weekly 13 needs 52 weekly observations; daily 30/60 need 90/180. Exact context/horizon counts must govern the adapter. [Pinned configuration table below](#ttm-r3-exact-branch-eligibility).
- **NPF is public with unknown license and different horizon semantics.** Its card defines 1m as four weeks and 3m as 13 weeks. Its overall TD target includes bugs, vulnerabilities and code smells, so it is broader than a maintainability-only target. Neither calendar-month nor daily labels may be silently substituted. [NPF card](https://huggingface.co/datasets/MaramAllah/NPFDataSet).
- **Tesoro GraphCodeBERT produces four debt-type signals, not a clean/debt classification.** Checkpoint license remains undeclared; upstream MIT code does not settle weight permission. Keep this optional classifier outside the forecasting-critical path. [Checkpoint API](https://huggingface.co/api/models/NamCyan/graphcodebert-base-technical-debt-code-tesoro), [author schema](https://github.com/NamCyan/tesoro/blob/main/data/README.md).

## Chronos-small input, missingness and output adapter

The current repository separately lists original `amazon/chronos-t5-*`, Chronos-Bolt and Chronos-2 models. Chronos-2-small uses the `chronos-forecasting` package and current Chronos-2 API; do not transfer original T5's 512 context or sampled trajectories to it. CPU/GPU inference is documented for Chronos-2, but no retrieved source establishes a numeric minimum CPU, RAM or acceptable MVP latency. [Publisher repository](https://github.com/amazon-science/chronos-forecasting), [full Chronos-2 card](https://huggingface.co/amazon/chronos-2).

`predict_df` consumes long-format ID, timestamp and numeric target columns. Extra history columns automatically become past covariates; columns shared with `future_df` become known-future covariates. Future rows must match IDs and horizon. Timestamps must be regular, same frequency, without row gaps. Output columns are ID, timestamp, `target_name`, `predictions`, and string quantile names. **`predictions` uses the 0.5 quantile despite the internal name `mean`.** `predict` returns `(variates,Q,H)`; `predict_quantiles` returns `(variates,H,Q)` plus `(variates,H)` point forecasts. Deciles are selected natively; arbitrary requested quantiles can be interpolated. Explicit `freq` bypasses inference and is not validated against data. [Current pipeline, lines 763–962](https://github.com/amazon-science/chronos-forecasting/blob/main/src/chronos/chronos2/pipeline.py).

Source preserves numeric target NaNs; the model derives an observation mask from NaNs and substitutes masked zeros after patching. Thus a regular grid with a genuinely missing target retained as NaN is a source-supported input design; it still needs an eventual load/forecast smoke test. Missing targets must never become measured zeros or interpolated evaluation labels. The dataframe frequency utility requires at least one series with three regular timestamps when inferring frequency; explicit frequency can bypass that API condition. The TEST dataset skips training's `min_past + horizon` filtering. These are API mechanics, **not an evidence-based minimum useful history**. [Preprocessor](https://github.com/amazon-science/chronos-forecasting/blob/main/src/chronos/chronos2/preprocess.py), [masking model](https://github.com/amazon-science/chronos-forecasting/blob/main/src/chronos/chronos2/model.py), [frequency utilities](https://github.com/amazon-science/chronos-forecasting/blob/main/src/chronos/df_utils.py), [dataset modes](https://github.com/amazon-science/chronos-forecasting/blob/main/src/chronos/chronos2/dataset.py).

Design implication: construct a narrow allowlist dataframe containing only intended inputs; passing a whole feature mart would accidentally expose label/status/path columns as covariates. Default to target-only, `cross_learning=False`, no `future_df`. Known-future covariates require information actually available at the forecast origin. Normalize to `(series_id,origin,target_timestamp,horizon_step,target_definition,point,q10,…,q90)` with point convention recorded as q50. q10–q90 is a **nominal 80% prediction interval**, not proven local coverage. API validation and domain eligibility are separate gates.

Current manifest: Python≥3.10; Torch≥2.2,<3; Transformers≥4.41,<6; Accelerate≥1.1,<2; NumPy≥1.21,<3; pandas≥2,<4; einops≥0.7,<1. The config's Transformers4.49.0 is publisher metadata, not a reproducible package lock. Exact runtime pinning and CPU compatibility checks are deferred implementation work. [Manifest](https://github.com/amazon-science/chronos-forecasting/blob/main/pyproject.toml).

Config declares `RobertaForSequenceClassification`, four generic `LABEL_n`, inconsistent two-entry `label2id`, multi-label classification and514 position embeddings. ## Dataset availability and target/timestamp caveats

**Technical Debt Dataset V2.** Official README describes31 projects, master-branch-only V2, SQLite format and raw tool outputs with no duplication/issue filtering; V1's branch/timeline warning should not be imported as V2 quality assurance. It declares **CC BY-NC-SA4.0** and research-purpose use. API release2.0.1 (2021-11-04) exposes `td_V2.db`,1,542,533,120 bytes; availability was checked as release metadata only. Its `SONAR_ANALYSIS.REVISION` joins analysis keys to Git commits; use this mapping instead of treating Sonar issue timestamps as forecast observations. [README](https://github.com/clowee/The-Technical-Debt-Dataset), [exact2.0.1 release](https://github.com/clowee/The-Technical-Debt-Dataset/releases/tag/2.0.1), [release API](https://api.github.com/repos/clowee/The-Technical-Debt-Dataset/releases).

V2 is a historical reconstruction source, not a ready daily/weekly forecast table. Define snapshot scope, active issue state, analyzer/rule compatibility, deduplication and units explicitly before aggregating. Issue closure reveals future outcomes; no closure information beyond origin may enter features. Current Sonar documentation distinguishes maintainability remediation effort from reliability/security effort; standard technical debt (`sqale_index`) concerns code smells and MQR uses `software_quality_maintainability_remediation_effort`. Estimates are rule-assigned effort, not measured labor or monetary debt. [SonarSource2026.5 metrics](https://docs.sonarsource.com/sonarqube-server/user-guide/code-metrics/metrics-definition).

**`MaramAllah/NPFDataSet`.** Public ungated API revision `00d1b3865d4b00d9f4a4733af7aaad8f7c90854a`, modified2026-09-15, lists `README.md` and `combined_td_mart.csv`; license is `unknown`. No full CSV was retrieved. The visible viewer advertises250k rows and four repository classes, while the card names six repositories; coverage remains unaudited. [API](https://huggingface.co/api/datasets/MaramAllah/NPFDataSet), [viewer](https://huggingface.co/datasets/MaramAllah/NPFDataSet).

Card specifies60 weekly snapshots from2015. Targets sum active bug+vulnerability+smell effort; horizons are3/4/13weeks. Exclude future label/status/path fields from features; enforce per-horizon `OBSERVED`, origin eligibility, chronological purge and feature timestamps≤origin. `t0` denotes historical commit date despite weekly scanning; regular timestamps need verification. Lineage is heuristic; identity counters are unimplemented. [Exact card](https://huggingface.co/datasets/MaramAllah/NPFDataSet/blob/00d1b3865d4b00d9f4a4733af7aaad8f7c90854a/README.md).

Design implication: separate snapshot time from commit time; reconstruct maintainability-only history/targets instead of relabeling all-issue TD. An endpoint label supplies no intermediate observations. If60 points are the complete usable series,52-context+13-horizon retrospective TTM scoring is unavailable. Treat NPF as secondary pending permission, scope and chronology verification.

## What this evidence permits

Use Chronos-small as the provisional single default with last-value/drift and justified seasonal baselines; defer optional TTM until sufficient complete cadence-specific observations exist. Freeze one measured target definition and analyzer/rules, retain missingness, score identical origins/horizons with MAE, decile quantile loss and nominal-interval coverage. Any minimum useful history, interval calibration, nonnegative postprocessing, CPU budget and improvement threshold belongs to the future evaluation protocol; none was established by metadata. No source proves maintainability forecasting efficacy, production readiness or acceptable performance on the unspecified hardware.
