# TechDebt360 research and architecture redesign

Completed design package, dated 2026-10-13. **Recommendation:** build an evidence-grounded Java technical-debt workbench with transparent prioritization and bounded, independently assessed remediation. Preserve a serious early study of imported repository-level forecasting. Reliable exact 90-day module forecasts are currently unsupported; no model's predictive or remediation superiority has been established.

No existing code, configuration or database was changed. No package installation, training, inference, build, scan or proof-of-concept experiment was performed. Future commands and milestones are plans only. The installed BMAD deep-recon, architecture and review methods were applied with independent source, data and architecture reviews. `_bmad` project helpers/configuration were absent, so configuration was not installed or initialized; standalone nonmutating lint/citation helpers were used.

## Fifteen final decisions

1. **What should it become?** A Java debt evidence workbench with source-linked measurements, review queues, assisted recommendations and exact verification records. Numerical forecasting is capability-gated.
2. **Most defensible direction?** Recommend the bounded evidence/remediation product and comparative study. Its scientific superiority remains a hypothesis; existing V2 histories deserve an early feasibility branch that can become the thesis if repair validation is impractical.
3. **Which pretrained models?** Qwen2.5-Coder-7B-Instruct is the first generator candidate. CodeRankEmbed is optional after demonstrated retrieval/patch benefit. No mandatory learned detector; specialist adapters remain gated. Conditional forecasters are Chronos-2-small/full and TimesFM2.5, with revision/context-qualified TTM-r3.
4. **Exact tasks?** Qwen explains and proposes bounded patches; CodeRank retrieves code evidence; a later admitted Tesoro model annotates four Java debt types. Forecasters predict supplied numerical measurements. None estimates actual labor from classifier confidence.
5. **Required data?** Immutable source, verified findings/domain, bounded same-snapshot context and meaningful baseline tests for repair; query/chunk relevance judgments for retrieval; independently reviewed compatible units for classification; measured, compatible, cutoff-aligned histories and independent future endpoints for forecasts.
6. **User outputs?** Current maintainability estimates, separate reliability/security, source and architecture evidence with coverage, transparent ranking factors, model-suggested annotations where validated, cited guidance, candidate patches and precise before/after checks. Forecasts/probabilities appear only with scoped validation.
7. **Reliable 90-day forecasts now?** Unsupported for the current real module workflow. Retained file rows mix 90/91/92 days; 1,361 exact90 rows correspond to only ten repository-origin clusters. Imported repository-level feasibility remains open, with substantial real numerical data.
8. **Integrate Chronos or Granite?** Benchmark conditionally after data/cadence gates; do not activate a production forecaster today. TTM's context means observations, not remediation minutes, and its branch must fit the native horizon. Select by measured value over strong baselines.
9. **Alternative when forecasts fail?** Bounded evidence/prioritization and independently evaluated repair. Debt-introduction and CMR prediction are secondary hypotheses needing their own valid labels, not automatic rescue targets.
10. **Can more history be acquired?** Likely for a bounded study: audit the existing V2 DB first, then recover already submitted operator tasks and pilot historical compiled scans. Long weekly backfill can cost hundreds of machine-hours; measure the small pilot before committing.
11. **Retain which modules?** Git/source inventory, missingness/provenance and exact export checks, causal lineage, immutable dataset publication and grouped/purged evaluation; retain lexical graphs as coverage-limited optional evidence. Preserve old experiments and version copies as read-only historical artifacts.
12. **Architecture?** Hexagonal modular monolith, one API/UI and durable worker, SQLite metadata plus immutable artifacts, isolated build/scanner/model runners, explicit analysis selectors, source-bound IDs, capability grants and immutable verification/approval tuples.
13. **Implementation order?** Audit and task/runtime checks; early imported-data gate; reliable evidence; optional annotations; bounded prediction/repair study; rankings; explanations/verification; API/UI; final evaluation. Failed optional model/history gates do not block useful measured assessment.
14. **Proof of research value?** Matched static/lexical/generator/retrieval ablations, independently judged evidence and patches, fixed-budget ranking utility, grouped uncertainty, and conditional persistence/tabular/foundation forecast comparisons. Report negative findings and failed/abstained cases.
15. **Remaining limits?** Original live scan recovery, historical domain/clock details, classifier licenses/labels, actual hardware/runtime, meaningful test coverage, independent reviewers, contamination and generalization. The UI states missing/partial/research-only/revoked capabilities, measured units and tests actually performed.

This package is complete as a research and design deliverable. Runtime, scientific and implementation gates intentionally remain future work; completion does not authorize development or assert successful experiments.
